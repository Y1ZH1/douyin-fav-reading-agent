## 1. 三种粒度的描述（按投递场景选）

### 1.1 一句话版（放在「项目经历」标题下）

> 基于本地抖音收藏转写库的阅读 Agent：Vue3 + Node 工具循环 / HITL / SSE，
> Python 负责转写与中文检索，Obsidian markdown 为源真相。

### 1.2 三行版（简历正文字数紧张时）

- 独立设计并实现「本地抖音收藏 → 可对话阅读」的 Agent 应用：Vue3 三栏界面 + Node Agent 循环 + Python 转写/检索工人，markdown 为唯一源真相，对话只落浏览器 IndexedDB。
- 自研 9 类事件的 SSE 协议驱动 6 态 Agent 状态机，前端用 ReadableStream 手写解析（需 POST 大 body + 可中断），替代只能 GET 的 EventSource。
- 落地人机中断（HITL）与「不确认不写库」的白名单机制，用 68 例测试把「模型不许越界做的事」钉死。

### 1.3 完整版（项目段落，约 8 行）

> **收藏阅读 Agent**｜独立开发｜Vue 3 + TypeScript + Pinia / Node + Express / Python + Flask + SQLite FTS5
>
> - **背景与定位**：已有一套 Whisper 转写 + Obsidian 笔记的本地管线，本项目在其上做**阅读层**——划线、解释、追问、入笔记、分类、检索，而不是再造一个采集器或「又一个 ChatGPT 壳」。
> - **编排与工人分离**：Node 持有 Agent 循环（意图分派 → 工具调用 → HITL → 流式回吐 → 行为落日志），Python 持有 ASR、落库与中文检索。换模型不碰工人，工人重活不阻塞 SSE 长连接。
> - **交互协议**：自定义 9 类 SSE 事件（`state / token / tool_call / tool_result / proposals / hitl_request / followup_suggestions / error / done`），前端按事件分派到三栏与各面板，状态机与视图完全解耦。
> - **人机中断**：分类采用双门槛判定（置信度 ≥ 0.72 **且** 与第二名间隙 ≥ 0.08 才自动写），未达标则弹出「选已有夹 / 新建 / 跳过」；任何对 `memory.md` 的写入必须显式 `approved`，缺参数直接 403。
> - **数据边界**：markdown 是源真相，对话存浏览器 IndexedDB，行为日志落服务端 `.state/`（**不进笔记库**）；检索命中默认只提案、不钉进上下文，避免整库灌 prompt。
> - **工程**：App/Index 分离使 HTTP 层可用临时端口起真实例测；单文件 < 500 行；跨语言格式契约用「Python 生成夹具 + Node 断言」锁死。68 例测试全绿，`vue-tsc` / `tsc` / `vite build` / eslint 全过。

## 2. 亮点拆解（每条：做了什么 → 难在哪 → 简历怎么措辞）

### 亮点 1｜编排与工人分离：把「Agent 循环」和「模型推理」讲开

**做了什么**
`server/src/agent.ts` 是循环本体：读 memory → 按 intent 分派 → 调工具 → 需要用户拍板就发 `hitl_request` 挂起 → 流式回吐 → 每条动作写行为日志。它之外没有任何「理解语义」的职责。Python 侧 `app.py` / `core.py` / `retrieve.py` 只管 ASR、落库、FTS/向量检索。

**难在哪**
绝大多数「Agent 项目」是一坨 prompt 套 while 循环。这里刻意让循环**不认识业务重活**：失败重试、HITL 挂起、SSE 背压都留在 Node；Whisper 这种 CPU 重活留在 Python。好处是工人宕了，阅读与划线仍可用（`getNote` 磁盘优先，Flask 只做兜底）。

**简历措辞**
> 采用「编排层 / 工人层」分离架构：Node 承担工具循环、人机中断与流式回吐，Python 承担 ASR 与中文检索。工人不可用时自动降级为磁盘直读 + 本地粗筛，而非整体不可用。

**面试会被追问**：为什么不把循环也写进 Python？
答：① 循环是 IO 密集（长连接 + 外部 LLM API），工人是 CPU/IO 混合重活，隔离后互不拖累；② 前端只需要一个同源入口，Node 天然是 BFF；③ 换 ASR 方案不动循环，换模型不动工人。

---

### 亮点 2｜自研 SSE 事件协议 + 状态机（最能体现前端功底的一条）

**做了什么**
9 类事件、6 个状态。前端 `useAgentRun.ts` 把「事件 → 状态」的映射收在一个 composable 里，视图只认状态：

| 事件 | 前端去向 |
|---|---|
| `state` | `agentState`（显示「正在调用工具 / 正在生成」） |
| `tool_call` / `tool_result` | 挂到对应助手消息的 `traces`，可展开看工具轨迹 |
| `proposals` | 候选托盘（**默认不钉**） |
| `hitl_request` | 弹确认卡，状态置 `hitl` 并挂起这一次运行 |
| `followup_suggestions` | 追问芯片 |
| `token` | 追加到助手消息（增量渲染） |
| `error` | 顶部错误条（文案是「问题 + 处理」两段式） |

**难在哪**
- **不能用 EventSource**：要 POST 一个可能带 8000 字正文的 body，EventSource 只能 GET。所以手写 `ReadableStream` + `TextDecoder` 解析，处理跨 chunk 的半截事件。
- **必须可中断**：`AbortController` 从 composable 一路透传到 fetch，用户点停要立刻停，且不弹错误。
- **`hitl` 是唯一「运行结束了但状态没结束」的态**：`finally` 里要判断 `agentState !== 'hitl'` 才置 `done`，否则确认卡会被当成已完成而消失。

**简历措辞**
> 设计并实现流式交互协议：手写 ReadableStream SSE 解析（支持 POST 大 body 与 AbortController 中断），以事件驱动的状态机解耦服务端事件与三栏视图，工具调用轨迹可追溯。

### 亮点 3｜人机中断（HITL）：把「自动化」和「别乱动我的东西」同时做到

**做了什么**
- 分类用 **Jev 式双门槛**：`confidence ≥ 0.72` **且** `confidence - second ≥ 0.08` 才自动写；否则中断，给「选已有夹 / 新建 / 跳过」。
- 改 `memory.md` 三条路径（用户说「记住」、设置页手改、行为日志编译）**全部**要确认；`PUT /memory` 没有 `approved` 直接 403 `RejectedWrite`，文案明写「未授权写入已阻止」。
- 入笔记时不知道写哪条视频 → 不猜，走 `note_target` 类型的 HITL。

**难在哪**
只卡置信度会让「0.75 vs 0.74」这种两夹胶着的情况被自动写错 —— 所以加第二道「间隙」门槛。更关键的是：**中断不是一个 `confirm()`**，它要能在服务端把这次运行挂起、把上下文交给前端、等用户回执后带着 `hitl.action` 重入同一个 intent，且中途不能丢状态。

**简历措辞**
> 设计人机中断机制：分类采用「置信度 + 与次优项间隙」双门槛判定，未达标即中断交人决策；对源真相文件（`memory.md`）的所有写入强制显式授权，未授权请求在 API 层直接拒绝。

---

### 亮点 4｜行为日志 → memory 自动编译（真正的「个性化」而不是「存个偏好」）

**做了什么**
7 类行为（划线解释 / 总结 / 入笔记 / 分类 / 检索 / 钉笔记 / 「记住」请求）以 append-only JSONL 落在 `server/.state/behavior-log.jsonl`。`compileMemory()` 把最近 N 天（默认 14）聚合成一份 **memory.md 草稿**：

1. **分类习惯**：同一目标夹被接受 ≥ 2 次 → 记下来
2. **解释偏好**：用户自定义提示词里高频出现的词（带停用词表）
3. **常查主题**：检索 ≥ 3 次才统计高频词
4. **使用节奏**：合计 ≥ 5 次才写一句
5. 用户显式说「记住 …」的原文，去重后收进来

**难在哪**
- **规则刻意保守**：只有「重复出现」才算习惯，单次行为不写。否则 memory 变流水账，反而污染每一次 system prompt。这是典型的「宁可漏，不可脏」。
- **草稿绝不落盘**：`compileMemory()` 的函数签名是「进文本、出文本」，它**没有能力**写文件。要落地必须走 HITL。这一点在测试里有专门用例。
- **可重复编译不叠加**：`stripCompiled()` 每次先摘掉上一轮生成的块，避免编译三次变成三层。
- **日志不影响主流程**：写日志包在 try/catch 里静默失败；4MB 自动轮转。

**简历措辞**
> 实现行为驱动的个性化记忆：把用户行为以 append-only 日志留痕，按保守聚合规则自动编译成记忆草稿（仅重复行为入档，避免污染 prompt），并强制经用户确认后才落盘。

**面试会被追问**：这不就是个 session state 吗？
答：不是。① 它跨会话、跨笔记；② 它**编译**而不是记录原始事件；③ 它写进的是模型每次都能看到的记忆文件，所以有「写脏了就持续污染」的风险，因此设了高门槛 + 人工确认。

### 亮点 5｜材料与会话分离（一条数据边界原则，贯穿全项目）

**做了什么**
- markdown 是**唯一源真相**：在 Obsidian 里随时能读原文，Agent 只是另一个读写者。
- 对话（消息、钉选笔记）存浏览器 IndexedDB，**绝不写进笔记库**。
- 行为日志落服务端 `.state/`，**不进笔记库**。
- 向量库 `state/retrieve-index.sqlite` 也在笔记库之外。

**难在哪**
这条原则约束了每一个功能的设计。例如「检索结果」很自然会想直接塞进上下文，但这里默认**只提案不钉**（`pinned: false`），钉不钉由用户勾选决定 —— 因为钉=长期上下文=每次请求都带上，整库灌 prompt 会既贵又糊。

**简历措辞**
> 确立并贯彻「材料 / 会话分离」的数据边界：源真相文件独立于会话记录，用户数据（对话、日志、索引）一律不写入笔记库；检索命中默认只提案，由用户显式钉选进入上下文。

### 亮点 6｜划线指纹 + stale 重匹配（技术含量最高的一条）

**做了什么**
划线不再以「正文里的裸引用」存储，而是进 frontmatter：

```yaml
highlights:
  - id: "h-1790500970601-c11ab2"
    quote: "换了个说法接着说同一件事"
    prefix: "<前 32 字指纹>"
    suffix: "<后 32 字指纹>"
    start: 42
    end: 54
    status: ok        # ok | stale
```

重新转写会覆盖正文，此时按**由强到弱**四级重定位：
`prefix + quote + suffix` → `prefix + quote` → `quote` → `quote + suffix`，
全都不中就标 `stale`（并去重，避免两条划线抢同一段）。统计 `{total, ok, moved, stale, duplicate}` 如实回报给用户。

**难在哪**
- **光用偏移不行**：重转写后所有偏移全失效。
- **光用 quote 不行**：同一篇里重复句子会撞车（所以有 `taken` 去重 + 四级降级）。
- **中文空白是个陷阱**：把空白折成单空格后，`怎么\n在` 变成 `怎么 在`，而正文里是 `怎么在` —— 会把好好的划线判成 stale。解法是**两种归一化都试**（`keep_space=true` 服务英文跨行，`keep_space=false` 服务中文跨行），并把归一化串上的下标映射回原文偏移。
- **两端必须一致**：`highlights.py`（Python，转写时迁移）和 `highlights.ts`（Node，界面上写划线）是同一套格式的两份实现，漂移就会把用户的划线写坏。

**简历措辞**
> 设计文本高亮定位方案：以「首尾指纹 + 字符偏移 + 四级降级匹配」应对源文本被重新转写后的大范围偏移，失败明确标记 stale 并如实回报，不伪造位置；跨语言（Python/Node）用「生成夹具 + 双端断言」的契约测试防止格式漂移。

### 亮点 7｜向量检索是「可选叠加」，且能自证有没有用

**做了什么**
- 不装向量也能用：FTS5 全文索引是基线，向量只是叠加层。`_embed()` 任何失败都返回 `None` 并静默退回 FTS。
- **一键安装**：`vector_setup.py` 建独立 venv（`state/venv-vector`）、装 `sentence-transformers`、下 `BAAI/bge-small-zh-v1.5`（清华 pip 源 + hf-mirror），装完把 site-packages 挂进 `sys.path` —— **不换解释器、不重启服务**。
- **自监督评测**：从每篇笔记正文取最长的中文片段当 query，期望命中它自己，量出 recall@k / MRR，给出 FTS vs FTS+向量的 `delta_recall`。
- 前端 `VectorPanel.vue`：状态 / 一键装 / 卸载 / 重建索引 / 跑评测，安装走 job + 轮询日志尾部。

**难在哪**
「向量检索」最容易被写成一个漂亮但没法验证的功能。这里把它做成**可度量**的：有基线（FTS）、有评测集（自监督，不需要人工标注）、有结论（delta_recall），且明确「没装也照样能用」。

**简历措辞**
> 将语义检索实现为可降级的叠加层（基线为 FTS5，向量异常静默回退），提供一键环境引导与自监督评测（自动构造 query 集，输出 recall@k / MRR 与相对基线的增益）。

### 亮点 8｜降级路径与「诚实性」

**做了什么**
- Flask 没开：`findCandidates` 退回本地词面粗筛，读文件头 12KB 打分，结果标 `via: 'local'`，前端**黄色警示**明说「这是本地粗筛，不是全文索引」。同时发一条「问题 + 处理」的错误：`先开 douyin-fav-transcribe 再重试；若已开，可能是索引未建，点「重建索引」`。
- 检索零命中：**明确说没命中**，「我不会编造出处」，且不发候选事件（有测试卡这条）。
- 顶部开机自检横幅：转写服务在不在 / 索引建没建 / 向量装没装 / 两边库路径是否一致 / 库里有没有笔记 —— 分级（错误 / 警告）+ 带动作按钮。

**简历措辞**
> 为所有外部依赖设计降级路径：服务不可用时降级到本地兜底并向前端如实标注数据来源，错误信息统一为「问题 + 处理动作」，避免静默失败与结果冒充。

### 亮点 9｜工程约定（体现「能长期维护」而不是「跑个 demo」）

- **单文件 < 500 行**：`AgentView.vue` 394 → 319 行，拆成 `components/agent/*` 8 个组件 + `useAgentRun.ts` + `agent-api.ts` + `types/agent.ts`。「布局」和「事件分派」彻底分家。
- **App / Index 分离**：`app.ts` 只装配、`index.ts` 只 `listen` → HTTP 层能用 `createApp().listen(0)` 起真实例测（31 例里 16 例是真实 HTTP 测试）。
- **测试卡「规矩」不卡「功能」**：
  - 没 `approved` 就写不了 `memory.md`（403）
  - `memory_patch` 第一轮只发 HITL，笔记库必须没被改
  - 空库检索必须承认没命中，且不许发候选
  - `../` 路径穿越必须被拒（`PathEscape`）
  - 重转写后划线要么跟着走、要么标 stale，不许假装还在原位
- **API 层不抛异常**：`Fetched<T>` 结构化返回（`{ok, data, error}`），因为「服务没开」是正常状态不是异常，视图要能区分「空结果」和「请求失败」。

## 3. 面试可能追问的问题（备好答案）

| 问题 | 答案要点 |
|---|---|
| Agent 循环为什么不用 LangChain / 现成框架？ | 循环只有 5 段，手写更可控；HITL 挂起、「不确认不写库」这类业务红线需要在状态机里显式表达，框架反而要绕着走。 |
| 你的「工具调用」是真的 function calling 吗？ | 刻意不用原生 function calling：① 意图由 UI 入口直接给出（点划线工具条 → `explain`），比让模型猜更准；② 分类这一个需要结构化输出的场景用「强制 JSON + 容错提取（剥 ```json 包裹）」。 |
| 怎么防止模型胡编检索出处？ | 三层：system prompt 明确「不要编造检索出处」；检索零命中时**不发候选事件**；检索结果默认不钉进上下文，钉选与否由用户决定。 |
| 为什么对话不落库？ | 源真相文件要保持「人能读、工具能改」的单一职责。会话是过程产物，塞进笔记库会污染 Obsidian 的检索与图谱。 |
| 记忆会不会把不好的习惯记进去？ | 所以有双保险：编译规则门槛高（重复出现才算）+ 落盘必须人确认。 |
| 性能上踩过什么坑？ | `getNote` 最初用「列出全部笔记再 find」，真实库 179 篇 → 每轮对话读几百次全文。改成「只读文件头 2KB 建 aweme_id 索引 + 15s TTL」，cold 62ms / warm 0.1ms；健康检查也从全库读正文改成纯 `stat`。 |

### P0 —— 补闭环（做掉 2-3 个就够撑起「上线后迭代」这一问）

| # | 优化项 | 为什么值得做 | 落地要点 |

## 5. 如果只做三件事

按「投入产出比」排序，做完这三件，这个项目从「功能完整」变成「有迭代故事」：

1. **冷启动入口**（P0-1）—— 堵住新用户第一眼是空态的问题，改动小、感知强。
2. **补 E2E 测试**（P1-5）—— 让「重转写 → 重匹配」这条最容易坏的链路有回归保护，直接对应亮点 6。
3. **评测基线留档**（P0-4）—— 让「向量到底有没有用」这个问题有历史数据可答，直接对应亮点 7。

这三件恰好各对应一个已有亮点，做完之后每个亮点都能补上一句「并且我验证过 / 并且它不会退化」。
